# Operations And Lifecycle Convention

## 1. 为什么这份规范要提前制定

除了目录、编码、依赖和文档规范外，个人工具仓库很容易在“能跑”之后迅速变乱。真正决定可维护性的，往往是运行约定和生命周期约定。

## 2. 建议提前锁定的额外规范

### 2.1 工具清单规范

每个 tool 必须提供 `tool.json`，声明：

- `tool_id`
- `name`
- `version`
- `entrypoints`
- `capabilities`
- `input_schema`
- `output_schema`

### 2.2 运行协议规范

提前定义：

- 参数传递方式
- 工作目录规则
- 标准输出 / 标准错误用途
- 退出码含义
- 结果文件落点

补充要求：

- dashboard 与 tool 的默认 `cwd` 应为主体项目目录
- `launchers/` 中的包装脚本必须负责修正运行目录
- Python 入口不应只隐式依赖当前工作目录，必须能接收显式 `project_root`

### 2.3 日志规范

建议统一：

- 日志级别：`DEBUG` / `INFO` / `WARNING` / `ERROR`
- 每行日志至少包含时间、级别、来源模块
- 需要被 dashboard 聚合展示的日志应支持结构化输出

### 2.4 配置规范

配置应分层：

- 仓库默认配置
- 用户级配置
- 运行时临时配置

同时明确：

- 配置优先级
- 配置文件位置
- 敏感信息是否允许入库

### 2.5 缓存与产物规范

提前区分：

- cache：可删、可重建
- artifacts：结果产物
- logs：运行记录
- examples：示例，不是运行缓存

缓存和产物默认也应相对主体项目目录或显式运行目录组织，避免散落到工具仓库根目录。

### 2.6 版本与迁移规范

对以下内容建议强制带版本：

- `tool.json`
- request / response schema
- preview schema
- 长期保存的数据文件

若 schema 升级，要明确是否兼容旧版本，以及是否需要迁移脚本。

### 2.7 错误码与异常映射规范

至少统一：

- `0`：成功
- `2`：参数错误
- `3`：输入文件错误
- `10`：业务失败
- `20`：内部异常

后续再按工具类型细化。

### 2.8 测试规范

建议从一开始区分：

- 单元测试
- 契约测试
- dashboard-tool 集成测试
- 样例回归测试

### 2.9 启动脚本规范

建议从一开始区分：

- `launchers/`：工作区项目运行入口
- `scripts/`：仓库维护脚本
- tool 独立 launcher：仅对具备独立运行边界的 tool 提供
- 非独立 tool：强制经由 dashboard 唤起

## 3. 结论

除了你已经列出的六类规范，我认为最值得提前补上的还有：

1. 工具清单规范
2. 运行协议规范
3. 日志规范
4. 配置分层规范
5. 缓存与产物规范
6. 版本与迁移规范
7. 错误码规范
8. 测试分层规范
9. 启动脚本规范
