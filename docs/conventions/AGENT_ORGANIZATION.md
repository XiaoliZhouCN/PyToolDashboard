# Agent Organization Convention

## 1. 目标

本规范定义仓库内多 Agent 协作时的默认组织方式，用于约束：

- Agent 类型与人数编制
- 不同 Agent 的职责边界
- Agent 之间的目录归属
- Agent to Agent 沟通文档的存放方式

该规范的目标是减少多 Agent 并行开发时的职责重叠和边界漂移。

## 2. 默认 Agent 编制

每个仓库默认采用以下组织方式：

```text
1 个架构维护 Agent
1 个框架建构 Agent
n 个专项开发 Agent
1 个验证文档 Agent
```

说明：

- `n` 由框架建构 Agent 根据当前任务拆分决定
- 若仓库当前规模较小，可以阶段性由较少 Agent 覆盖这些角色
- 即使由同一个实际执行者承担多个角色，也应在职责上区分这些角色

## 3. Agent to Agent 目录要求

每个仓库都应维护一套专门的 Agent 沟通目录，推荐位置：

```text
docs/architecture/agent_to_agent/
```

该目录用于存放：

- 架构沟通文档
- Agent 职责说明
- 目录归属记录
- Agent 间交接说明
- 评审与验证回复

维护规则：

- 该目录主要由架构维护 Agent 负责创建和维护
- 其他 Agent 不应随意改写整体规则，但可以在约定的文件中补充回复
- 若某项规则已成为稳定约束，应上收至 `docs/conventions/` 或 `docs/architecture/`

## 4. 四类 Agent 的职责边界

### 4.1 架构维护 Agent

职责：

- 维护仓库级架构边界
- 维护 Agent 组织方式与沟通规范
- 维护模块职责划分、依赖方向和目录归属
- 输出和更新架构类文档

限制：

- 不参与具体功能代码实现
- 不负责具体 tool 业务开发
- 不直接承担专项功能交付

### 4.2 框架建构 Agent

职责：

- 搭建仓库基础框架
- 维护通用目录结构、骨架、模板和公共运行时
- 决定需要拆分出多少个专项开发 Agent
- 维护跨模块的框架层实现

限制：

- 不负责具体功能实现
- 不应替代专项开发 Agent 完成业务逻辑开发

说明：

- 框架建构 Agent 涉及全局框架，允许在必要时跨越多个顶层模块
- 但其改动应聚焦在“基础设施”和“框架层”，而不是具体产品能力

### 4.3 专项开发 Agent

职责：

- 负责具体功能开发
- 维护分配给自己的固定目录和文件
- 在既定框架下完成单一业务域或单一模块的功能实现

限制：

- 不应越权修改其他专项开发 Agent 负责的目录
- 不应直接重构全局框架边界，除非经过框架建构 Agent 或架构维护 Agent 明确调整

目录边界规则：

- 不同专项开发 Agent 的主责目录不应重叠
- 所有专项开发 Agent 的主责目录总和，应能覆盖当前需要开发的代码范围
- 若某功能横跨多个 Agent 目录，应先由框架建构 Agent 重新切分职责或指定主责 Agent

### 4.4 验证文档 Agent

职责：

- 验证功能结果与约束是否一致
- 补充测试、验收记录和使用文档
- 维护对外说明文档和验证结论

限制：

- 不承担主要功能开发
- 若发现结构性问题，应反馈给架构维护 Agent 或框架建构 Agent 处理

## 5. 目录归属原则

多 Agent 协作时，代码目录应按主责清晰归属。

默认要求：

1. 专项开发 Agent 维护固定目录集合
2. Agent 与 Agent 之间的主责目录不允许重叠
3. 若存在共享逻辑，应上收至公共框架目录，而不是由多个 Agent 各自维护副本
4. 框架层目录可由框架建构 Agent 维护，必要时允许跨模块
5. 架构维护 Agent 维护文档边界，不维护业务代码目录

## 6. 例外规则

以下情况允许例外，但必须显式记录：

- 框架建构 Agent 需要调整跨模块骨架、模板、shared runtime 或 contracts
- 架构维护 Agent 需要修正文档结构、Agent 沟通目录或架构类规范
- 紧急问题需要临时跨目录修复，但后续必须回归主责划分

例外应尽量记录在：

- `docs/architecture/agent_to_agent/`
- 或相关架构文档中

## 7. 合理性判断

本规范整体是合理的，原因包括：

1. 将“架构维护”和“框架建构”分离，可以避免架构文档与基础实现混在一起
2. 将“专项开发”限定为固定目录主责，可以降低并行开发冲突
3. 将“验证文档”单独成角，可以减少“开发者自己验自己”的盲区

但也应注意：

1. 对于很小的仓库或很短周期的任务，不应机械追求完整编制
2. 目录主责不重叠是默认规则，不代表任何临时协作都被禁止
3. 若角色过多而任务过小，会增加沟通成本，应允许按阶段简化
