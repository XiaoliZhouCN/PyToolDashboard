# Code Style Convention

## 1. 通用风格

- 编码：`UTF-8`
- 缩进：空格，Python 为 4 空格；Web 资源为 2 空格
- 换行：`LF`
- 单行长度：建议不超过 100 字符
- 注释：仅在逻辑不自明时添加简洁注释

## 2. Python 命名规范

| 对象 | 规范 |
| --- | --- |
| 模块文件 | `snake_case.py` |
| 包目录 | `snake_case` |
| 函数 | `snake_case` |
| 变量 | `snake_case` |
| 常量 | `UPPER_SNAKE_CASE` |
| 类名 | `PascalCase` |
| 私有成员 | `_leading_underscore` |

额外约束：

- 布尔变量优先使用 `is_`、`has_`、`can_` 前缀
- 避免使用单字母变量，循环计数器除外
- 缩写要稳定，例如统一使用 `config`，不要混用 `cfg`

## 3. Python 可维护性规范

Python 代码不仅要能运行，还要让“人类维护者”能够快速读懂、修改和排查问题。

核心要求：

- 优先写**清晰可读**的代码，而不是炫技式写法
- 优先让函数、变量名和模块结构表达语义，减少阅读者推理成本
- 单个函数应尽量只做一件事，避免混合参数解析、业务逻辑、I/O 和格式转换
- 优先使用显式流程，而不是过度压缩的一行表达式或层层嵌套推导式
- 当实现中使用了算法、设计模式或非直观技巧时，应让结构和命名足够明显，必要时补一行说明其目的

推荐实践：

- 复杂流程拆成若干语义明确的小函数
- 优先返回结构化结果，而不是临时拼接的松散字典
- 对关键分支和边界条件写清楚意图
- 如果某段逻辑未来很可能变化，优先用更容易替换的组织方式

不推荐：

- 为了“短”而牺牲可读性
- 在一个函数里混杂过多职责
- 使用阅读门槛很高、但收益不明显的技巧

## 4. Python 注释与文档字符串规范

注释的目标是帮助维护者更快理解“为什么”和“边界”，不是把代码逐句翻译成自然语言。

### 4.1 函数说明

对于公共函数、入口函数、关键业务函数，建议在函数上方使用文档字符串，说明：

- 函数作用
- 关键参数语义
- 返回值语义
- 必要时补充副作用、异常条件或使用限制

推荐形式：

```python
def build_preview_records(source_path: Path, limit: int) -> list[PreviewRecord]:
    """Build preview records from a source file.

    Args:
        source_path: Input file path resolved from project_root.
        limit: Maximum number of records to return.

    Returns:
        A list of normalized preview records for dashboard display.
    """
```

### 4.2 行内注释

只在以下情况添加简洁注释：

- 这段逻辑的目的不容易从代码表面直接看出
- 这是一个边界条件处理
- 这里有协议约束、格式约束或运行目录约束
- 这里使用了算法技巧、缓存策略、惰性计算等非直观实现

要求：

- 注释优先解释“为什么”，而不是“这行代码做了什么”
- 注释应简短、直接、与代码同步维护
- 不为显而易见的赋值、判断、循环写注释

### 4.3 什么时候必须补说明

以下场景建议强制补充文档字符串或注释：

- tool 的入口函数
- dashboard / tool 的调度入口
- 涉及 `project_root`、工作目录切换、路径解析的逻辑
- 复杂数据转换、协议组装、schema 兼容分支
- 使用明显算法或设计模式的关键实现

## 5. Python 优雅性规范

这里的“优雅”不是追求花哨，而是追求：

- 结构清楚
- 抽象适度
- 扩展点明确
- 读者容易建立心智模型

允许并鼓励：

- 在必要时使用成熟算法
- 在确实能降低耦合或提升可扩展性时使用设计模式
- 提前把易变逻辑隔离到独立函数、类或适配层

但必须满足：

- 抽象带来的收益要大于理解成本
- 模式服务于问题，而不是为了“用模式而用模式”
- 如果一个简单方案已经足够清晰，不要过度架构化

建议判断标准：

- 新同事或未来的自己，能否在短时间内理解这段实现
- 修改一个局部需求时，是否需要牵连很多不相关代码
- 出现 bug 时，是否容易定位到职责边界

## 6. Web UI 命名规范

- TypeScript / JavaScript 变量与函数：`camelCase`
- 组件名：`PascalCase`
- CSS class：推荐 `kebab-case`
- 文件名：
  - 组件：`PascalCase.tsx`
  - 非组件模块：`camelCase.ts` 或 `kebab-case.ts`

## 7. C++ 命名建议

为未来接入 C++ 预留统一口径：

- 类型名：`PascalCase`
- 函数名：项目内统一后保持一致，可选 `camelCase`
- 常量：`kUpperSnakeCase` 或 `UPPER_SNAKE_CASE`，项目内必须单一
- 文件名：`snake_case.cpp/.h` 或项目前缀风格，避免混杂

## 8. 代码组织规范

- 入口层负责解析参数、调用服务，不承载核心业务
- 核心业务尽量纯函数化、可测试
- I/O、外部进程、网络、文件系统访问放在 `infra/` 或适配层
- 不在 UI 层直接堆业务逻辑
- 面向人类维护者组织代码，优先按职责拆分而不是按个人习惯堆叠
- 复杂实现应让文件名、类名、函数名与职责对应
- 若引入设计模式或通用抽象，应在命名和文档字符串中体现其角色

## 9. 格式化工具

- Python：`ruff format`
- Python lint：`ruff check`
- 后续如接入 Web UI，可按子项目选用 `eslint + prettier`
